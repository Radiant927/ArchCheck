# ArchCheck 开发计划书 —— BIM 输入 + DeepSeek 接入

> 目标：让平台处理**真实场景**——输入 BIM（IFC）而不是 2D 图纸，并接入真实大模型（DeepSeek），同时守住合规判定的严谨性。
> 老师的要求：① 不能只输入 2D 图纸，要模型读 BIM；② 平台要有真实模型参与。
> 现状：规则引擎 + 多智能体架构已完成（CN 20 项 / SG 14 项），代码已模块化（`core/`）并推送 GitHub。

---

## 一、核心设计立场（跟老师对齐的关键口径）

**合规判定必须确定性，不能用 LLM 判数值。** 规范是精确阈值（门宽 ≥0.9m、疏散距离 ≤30m），合规审查要求可解释、可审计、可复现；LLM 做数值判定会不稳定、会幻觉。所以：

> **模型负责「读」和「说」，规则引擎负责「判」。**

DeepSeek 的角色定位为三件事（都是 LLM 真正擅长的）：
1. **审查叙述**：规则引擎的判定结果 → 自然语言专业审查意见 + 整改说明
2. **规则生成**：规范条文 → JSON 规则（支撑"新增标准不改代码"卖点）
3. **协调器升级**：LLM 汇总四 Agent 结果、解释跨专业冲突、给协同处置建议 → 让"多智能体"成为真·多智能体

**部署口径**：架构上支持"本地可部署"（Ollama 后端），演示走 DeepSeek 官方 API（已在 `llm/client.py` 预留可切换后端）。答辩表述建议："支持本地部署，演示采用 DeepSeek API"。

## 二、三层架构

```
BIM/IFC 文件（.ifc）
    │
    ▼  ① 解析层  bim/parser.py（ifcopenshell，确定性）
楼层 / 空间(面积) / 门 / 墙 / 防火分区(IfcZone) → 结构化 JSON
    │
    ▼  ② 判定层  core/engine.py（现有规则引擎，不改）
Civil · EEE · Building · Coordinator
    │
    ▼  ③ 模型层  llm/client.py（DeepSeek，OpenAI 兼容）
审查报告叙述 · 规则生成 · Coordinator LLM 协同
```

## 四、必须主动跟老师讲清的现实坑（避免答辩被追问）

1. **IFC 给的是建筑骨架**（空间/面积/门/几何），疏散路径、防火分区归属、电气负荷/插座/水源距离这些合规参数**通常不在 IFC 里**。
   - 处理：能用几何/算法算的（疏散路径=空间邻接图最短路）用算法算；算不了的让 DeepSeek 依据规范+建筑图**推理给出假设、人工确认**，或作为属性补录。
2. **消防/电气专业构件**常需在 Revit/BlenderBIM 建模时带上，或作为自定义属性补录。
3. **"本地接入" vs API** 的口径（见第一部分）。
