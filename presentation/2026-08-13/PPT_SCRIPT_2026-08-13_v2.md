## 页② 上周的两个问题 → 为什么今天的方案能解决（3 分钟 · 重点页）



**【讲解词】**

>
> **第一个问题，数据源。**
我们读的介质错了，应该读模型，而不是读图纸。**
>
> **第二个问题，判定方式。** 我们当时让通用大模型直接判规范。大模型会"一本正经地编"——我们实测，原来规则里引用的 Fire Code 条款号，**6 处全部指向错误的内容**。而且它判的结果每次都不一样，**不可复现、不可审计**；覆盖范围也小。所以问题也很清楚：**判定不能交给会幻觉、不可复现的大模型。**
>
>
>
> **针对数据环节**——两个动作：
> 第一，**自己生成 IFC 样例**，把 BIM 文件里到底存了什么、长什么样彻底搞清楚；
> 第二，实现一条**确定性的解析算法链**，把模型里的数值一个一个抠出来。
> 这解决的是——**数据从哪来、读得准不准**。
>
> **针对判定环节**——也是两个动作：
> 第一，把规范本身做成**知识库（RAG）**，让每一次判定都有规范依据、可追溯。
> 第二，制定了**确定性的规则引擎**；
>
> 一句话总结这一页的路线：**问题在"数据"和"判定"两个环节，方案就分别打在这两个环节**。下面四页，前两页讲数据环节，后两页讲资料与判定环节。

## 页④ 读取 IFC 的算法链：怎么把模型"读成一张表格"（2.5 分钟）

**【页面要点】** 9 步算法链 + QA + 输出。

这一页展示的是我们读取 BIM（IFC）模型的整套解析算法流程。
第一步先打开 IFC 模型，自动识别长度单位；如果模型里没写明单位，我们就依靠楼层标高自动推算，区分米或者毫米。
接着按 BIM 标准里两种完全不同的关联关系，分开提取两类元素、绑定到对应楼层 —— 这就是我们之前踩过的关键坑：
房间属于空间对象，用聚合关系挂靠楼层；
墙、门窗、梁柱这类实体构件，用空间包含关系挂靠楼层；
两种关系不能混用，一旦选错，程序就识别不出房间。
拿到房间轮廓之后，我们把三维空间投影到水平面，再用鞋带公式计算房间面积，异形房间也能算出准确值。
读取门宽时我们设计了三级兜底逻辑：优先读取模型自带标准尺寸，读不到再从名称提取，实在不行就靠几何体自动测算。
然后建立门和房间的关联：优先读取 BIM 原生的空间边界关系，读取失败就依靠几何位置兜底匹配。
基于房间和门的连通关系构建邻接图，算出疏散距离，同时提取梁柱的截面、跨度这类结构参数。

整套解析跑完，我们会做四项模型可用性校验，输出 0-100 分的模型健康度，遇到致命问题直接阻断后续判定。
最终输出规整结构化数据，直接交给我们自研的 JSON 规则引擎，开展消防、无障碍等规范合规审查。

## 页⑤ 资料端：用一个案例，把"数据对规则"走一遍（2.5 分钟）

这一页介绍我们项目的规范资料端，也就是支撑判定依据的 RAG 知识库

首先是文件目录结构，我们按地域和用途分类存放规范；再往下细分建筑管控、消防安全、无障碍、可持续性、施工可行性这五大类，原始材料保留 PDF，同时预处理成文本方便检索。
第二块是 RAG 知识库的完整搭建步骤。
我们优先从政府官方渠道搜集规范，区分免费全文和仅能拿到索引的付费文件；
完成原始内容采集。之后归档入库，再通过清洗脚本做文本规整，
最后通过检索脚本，根据审查时用到的规范编号，匹配并取出对应的原文证据片段。
第三部分，也是最关键的：资料端和前面 IFC 解析的数据端，靠统一字段契约对接。
BIM 解析输出结构化数据，比如门宽；规则 JSON 里定义好字段、运算符、阈值，以及对应的规范编号、。
系统做判定时，拿解析出来的实测值和阈值对比，同时关联 RAG 知识库，调出对应的规范原文

## 页⑥ 框架更新：为什么拆成 5 个 Agent + 一个案例 + 四专业特点（3 分钟）

接下来介绍我们更新后的 5 Agent 模块化架构，支持消防、电气、全楼、结构四大专业审查。
我们拆分 Agent 的核心目的，是避免单一模块职责过载、逻辑混杂。先说明：这里的 Agent不是自主决策的通用智能体，而是职责独立的流水线模块。
坚持核心原则：数据读取、合规判定、条文复核全部走确定性代码，保证结果可复现、可审计；大模型只做报告叙述，绝不参与数值判定，也没有使用 LangChain 这类 Agent 框架，规避随机风险。

五个角色分工清晰：
① BIM Reader：解析 IFC 模型，提取数据并校验模型健康度，异常模型直接阻断流程
② Compliance Judge：执行四大专业规则判定，检测跨专业冲突
③ KB Steward：维护规范 RAG 知识库、解析动态阈值，必要时 LLM 辅助兜底
④ Reasoner：依托大模型生成审查说明、协调专业冲突，不做合规判断
⑤ Independent Reviewer：用规范原文复核判定依据（概念保留，前端 UI 已移除）

最后说明四专业设计：
规则按消防、电气、全楼、结构分成独立 JSON 文件，方便分专业维护；引擎一次性载入全部规则，依靠字段自动匹配校验对象；这样的话后续新增专业只需增加规则文件，核心引擎无需改动，扩展性很好。

## 页⑦ 平面视图是怎么来的（1 分钟）

**【页面要点】** 3 步算法 + 数据驱动 + 边界。

这一页我们来解释，平台是如何将复杂的三维 BIM 模型，转换成大家现在看到的、用于审查的二维平面图的。

第一步，几何提取。我们使用ifcopenshell这个专业库，读取 BIM 模型中的三维空间实体，并将其曲面化，为后续处理做准备。
第二步，投影与凸包。我们将三维模型投影到水平的 XY 平面上，然后利用算法，为每个房间构建一个 “凸包”。简单来说，就是用一个最紧凑的凸多边形，把房间的轮廓包裹起来，方便后续计算。
第三步，计算与渲染。我们用经典的 “鞋带公式” 计算出房间的面积。最后，通过Pillow这个绘图库，将计算结果渲染成大家看到的楼层俯视图、3D 等轴测图，甚至建筑剖面图。

这样做的好处非常明显：
数据驱动：模型只要有任何修改，平面图会立刻更新，保证了审查结果和图纸永远是对齐的。
边界透明：我们也诚实地说明，由于使用了凸包算法，对于 L 型、U 型这类凹形房间，计算出的面积会有轻微的高估，这一点在我们的代码里已经做了明确标注。

## 页⑧ 遇到的问题：动态阈值（用案例讲清问题在哪）（2.5 分钟）
接下来介绍项目落地时遇到的一个问题：主梁实测梁高 0.24m、跨度 4.08m。
如果用传统固定比例的死板规则，按跨度除以 10 计算，阈值约 0.41 米，会误判这根梁不满足要求；
而我们改用贴合规范逻辑的动态公式max(0.2, min(跨度,6)/20)，算出阈值 0.204m，实测 0.24m 大于阈值，判定合格，结果和工程实际一致。
为什么一定要做动态阈值？
第一，BIM 提取的几何长度不等于设计意图，很容易引入数据噪声，造成大量虚假违规；
第二，很多规范本身就是比例关系式，不是简单固定数值，用动态公式更贴合规范本源逻辑。
我们也划分清楚了使用边界：
像柱截面、板厚、最小水源距离这类固定构造限值，直接用静态阈值；
梁跨高比、疏散距离、分区面积这类随条件变化的比例指标，才启用动态阈值。
同时定下约束纪律：动态公式必须设置构造底线、写明前置假设，所有参数和逻辑都留存文档可追溯。

IFC 只输出构件「几何外形尺寸」，但规范审查依赖「工程语义 / 受力意图」；简单拿几何全长直接套固定阈值，就会产生假阳性误判。

## 页⑨ 下一步（1 分钟）

**【页面要点】** 4 个方向。

第一，完善 RAG，新增语义检索。目前只用关键词匹配，只能粗定位到章节；后续引入 Embedding 向量检索，提升规范证据匹配的准确率。
第二，付费规范的接入方案，需要做版权权衡。现阶段付费标准只保留索引，审查结果提示人工查阅原文；后续在采购全文、结构化索引、人工复核三种方案里权衡落地。
第三，把证据定位从「字段级」升级到「条款级」。现在判定依据只标注标准名称，目标是直接锚定到规范第 X 条原文，让证据链路更精准。
第四，优化平面图算法。当前凸包算法会轻微高估凹形房间面积，后续改用多边形布尔裁剪运算，提升轮廓与面积计算精度。

## 附 1：被追问时的预判问答（备用）

**Q：为什么不直接让大模型判定？**
> 大模型是生成式的，同一问题每次回答可能不一样，还会编造（FC23 6 处条款号全错就是证据）。合规审查要可复现、可审计，所以数值判定交给确定性规则引擎，大模型只写报告。

**Q：你的 RAG 是真正的向量检索吗？**
> 目前是关键词全文检索，证据只能定位到"标题/章节"层面，定位不到条款。语义向量检索是我们下一步第一项，目前如实说明。

**Q：动态阈值会不会绕过规范？**
> 不会。分界线是：绝对量（构造底线）必须静态，比例量（随跨度/面积/路径变化的）才动态；动态公式带构造底线、公开假设，已写进决策文档请导师确认。

**Q：付费标准没全文，是不是审不了？**
> 涉及付费标准的判定，系统明确标注"请查阅原文"，由人工核对。这是版权合规下的诚实选择；免费标准有全文，能自动出证据。

**Q：自建 IFC 算不算糊弄？**
> 口径分开：自建样例做回归测试、验管线通不通；真实样例（FZK、Snowdon）验真实感。两者用途不同，不混着说。

## 附 2：字段定位 vs 条款定位（通俗版，自备理解用）

- **字段定位（现在）**：我知道"门宽这个字段 = 0.885，小于阈值 0.9，判违规"，规范依据只挂到"标准名"（如 GB 50016）。就像知道"这道题判错了，依据是《数学手册》，但没说哪一页哪一条"。
- **条款定位（目标）**：能给出"依据 GB 50016 第 5.5.18 条，原文『……』"。就像能说出"依据《数学手册》第三章 3.2 节：『……』"。
- **为什么现在做不到**：①付费标准无全文，拿不到条文；②免费标准只做了关键词取片段，没做条款级分段编号；③条款号核实成本高、风险大（FC23 教训）——宁可只到标准名，不冒险编。
- **怎么实现**：规范文本按章/节/条切分编号 → 语义向量检索把判定上下文匹配到具体条款 → code_ref 升级为"标准名 + 条款号"。
