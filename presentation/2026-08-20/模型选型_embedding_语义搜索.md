## 一、模型选择对检索准确率的影响程度（如实）

Embedding 模型是语义检索的"度量衡"：把 query 和条文都映射到向量空间，准确率 = 模型把"语义相关"的文本拉近、把不相关的推远的能力。影响程度按维度排序：

1. **语言覆盖（影响最大）** —— 单语模型对另一语言的语料基本失效。我们的语料**大部分是英文（Fire Code 2023 ≈ 991KB）**，中文只占少部分（GB 55037 ≈ 102KB）。若用中文为主模型（bge-small-zh / m3e），英文 Fire Code 的语义召回会大幅掉点，几乎退回"碰关键词"水平。**选错语言族 = 语义搜索形同虚设。**
2. **规模 / 训练数据** —— 同族模型越大越强（bge-m3 568M > e5-small 118M），MTEB 多语言榜上 bge-m3 明显领先；但到一定规模后边际收益递减。
3. **检索专项训练** —— 通用句向量（如 MiniLM）在检索任务上弱于专项检索模型（bge / e5 都是为检索设计的）。
4. **长文本支持** —— bge-m3 支持 **8192 token**，可索引更长条款；512 ctx 的模型（e5-small）需要把条款切得更碎，切块边缘信息易丢。

> **诚实声明**：尚未在本平台语料上跑"逐模型统一评测集"对比；以下选择依据 = MTEB / MIRACL 公开榜单 + 模型特性 + 语料构成（英为主、中为辅）。

---

## 二、为什么选 bge-m3

1. **多语言检索最强开源模型之一**（MTEB 多语言 / MIRACL 榜前列），**中英都覆盖** → 正好匹配平台双语（CN GB 中文 + SG FC23 英文）
2. **8192 超长上下文**，对 Fire Code / GB 55037 长条款有利
3. **transformers 直接用**（CLS pooling），生态成熟、可离线推理、可复现
4. **开源权重、本地部署**，符合平台"数据真实、可复现"原则
5. **ModelScope 可下载**（国内 CDN 实测 200、稳定）→ 网络可行，无需再折腾代理

---

## 三、为什么之前的下载会失败（三条路径实测）

| 路径 | 实测结果 | 原因 |
|---|---|---|
| HuggingFace 直连 | 000 被墙 | huggingface.co 在本网络不可达 |
| HF 走代理 7890 | API 通（200），但**大文件卡死** | 代理能建连/查询，但 ~450MB 权重传输停滞（分块 0 字节，卡在 44M） |
| hf-mirror.com | 解析重定向通（308），**拉文件失败** | 重定向到的 CDN 也不可达（`LocalEntryNotFoundError`） |
| **ModelScope** | ✅ **稳定下载成功** | 国内 CDN，直接可达（bge-m3 2.2GB 正常拉取） |

**结论**：本网络下 HF 系（直连/代理/镜像）均不可靠，唯一稳定通道是 **ModelScope**。

---

## 四、为什么不选其它模型

| 模型 | 不选的原因 |
|---|---|
| `intfloat/multilingual-e5-small`（471MB） | 质量不错，但 **ModelScope 上没有**（404）→ 只能走 HF，而 HF 在本网络下载失败；且 118M 参数、512 ctx，多语言能力弱于 bge-m3 |
| `intfloat/multilingual-e5-large`（2.2GB） | 同量级，但需 HF（不可达）；MTEB 多语言不如 bge-m3 |
| `BAAI/bge-small-zh-v1.5`（95MB） | 中文为主、**英文弱** → 英文 Fire Code 检索明显掉点；只适合作"纯中文更轻"备选，不满足双语需求 |
| `moka-ai/m3e-small` / `m3e-base` | ModelScope 该路径 **404（不可得）**；且中文为主、英文弱 |
| `BAAI/bge-large-en-v1.5` 等单语系 | 只覆盖单一语言，不满足双语 |

---

## 五、结论

**选 `BAAI/bge-m3`**：多语言最强、ModelScope 可下载、可离线、生态成熟。代价是权重 2.2GB + CPU 一次性建索引稍慢（分钟级），可接受；查询阶段每次推理秒级，不影响使用。
