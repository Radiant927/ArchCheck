# 实测进展汇报：真实 MEP 模型读取、测评与规则闭环

> **一句话**：一个没有房间、没有系统标签、单位还混乱的真实机电模型，我们做到了实体 100% 读全，还揪出了一个"看着在查、实则没查"的规则死角，并补上了兜底规则。

> 日期：2026-09-06 ｜ 归属：`presentation/2026-09-08/`（下次汇报准备）
> 主题：用一个真实 IFC4.0 机电模型（Lab.ifc）验收平台，走通"读 → 测 → 查 → 修"闭环
> 原则：诚实标注，能做什么、不能做什么、为什么不能；所有数字可复算

## 一、背景与目标

**起因**：拿外部真实 IFC4.0 文件来验收平台。过去测试用的是自造/自选样例（`office_3f` 是自家生成、几何干净、有系统标签），这次换成一份**事先不知道内容**的真实导出文件——1.1MB 纯机电模型 `Lab.ifc`。

**核心问题**：我怎么知道这份文件**读全了没有、读得准不准**？这是整个工作的主线。

**工作顺序**（先完善再测评）：① 补全读取能力 → ② 建立测评机制 → ③ 跑通并发现问题 → ④ 补规则闭环。

## 二、测试对象：Lab.ifc 长什么样

先用 ifcopenshell（读取 IFC 文件的 Python 库）直接"数实体"，得到文件的真实账本：

| 内容 | 数量 | 说明 |
|---|---|---|
| 管道段 | **173** | 圆形截面 |
| 管道配件 | **135** | 弯头98 / 三通36 / 存水弯1 |

| 墙 / 门 / 窗 / 柱 / 板 | 12 / 3 / 1 / 3 / 2 | 建筑构件很少 |

**三个关键特征**决定了后面所有工作：
1. **MEP 为主**（416 个分布元件），建筑/房间几乎没有
2. **管道全无系统标签**（173 根 pipe_type 全 unknown——pipe_type 指管道的"用途标签"，如消防/给水/排水，是触发专项规则的开关）
3. **单位混乱**（声明毫米、几何却是米——见第三节）

## 三、第一环 · 读：补全 + 解决单位坑

### 3.1 原先读不到什么（账本 − 提取能力 = 缺口）

对照文件账本与旧提取器，发现 MEP 读取缺口：
- **管道配件（135 个）完全漏掉** —— 旧代码只读管段和风管
- **材料、数量集、风管截面尺寸**基本闲置
- 管道系统分类只认固定几个属性名，覆盖面窄

### 3.2 完善内容（本次落地的）

| 完善项 | 效果 |
|---|---|
| 补全 IfcPipeFitting 配件提取 | 135 个弯头/三通/存水弯全部读出，纳入 clash 检测（clash = 管道和墙/梁有没有"打架"撞在一起）|
| 管道/风管系统分类多源兜底 | Pset → 类型对象 → 材料 → 名称，四级找系统线索 |
| 风管截面精确提取 | 从横截面几何算宽高（此前全空） |
| 材料信息提取 | 管道/风管/配件材料读出（Lab 全为 PVC）|
| 激活 IfcElementQuantity 数量集 | 建模软件常把精确的"长/宽/高/面积"另存在数量集（Qto）里——有 Qto 时优先用这个精确值，几何估算降级为后备 |
| 数量校验、schema 兼容 | IFC2X3 / IFC4 都安全，不崩溃 |

### 3.3 单位坑：为什么一根水管会算出"116 米粗"？

**现象**：首次改进后读到一根管道 `diameter = 116.0`（米）——水管不可能 116 米粗。

**根因**：IFC 格式假设"一个文件一套单位"，但真实导出常混着两套。Lab.ifc 实测：

| 数据 | 声明说 | 实际是 | 按错刻度算的结果 |
|---|---|---|---|
| 墙/板世界坐标 | 毫米 | **米** | 板厚算成 0.0002m（纸片）|
| 管道截面半径 | 毫米 | 毫米 | Radius=58 → 直径 0.116m ✅ |
| 风管数量集 | 毫米 | **米** | 宽算成 0.00005m（头发丝）|

**解法（三层）**：
1. **世界坐标刻度**：读声明 + 抽样大构件几何交叉校验——若按声明单位算出来尺寸离谱（板厚 0.2mm），判定几何实际是米。
2. **局部参数单独刻度**：截面/数量集跟世界坐标可能不同单位，单独用一个"声明刻度"换算。
3. **抽样投票定局部参数单位**：抽管道+风管各 20 根，分别用两套刻度算、与几何量出的"外接盒"尺寸比对投票（外接盒 = 把每个构件框住的最小方盒，其长宽高不受单位声明影响）。Lab 结果是 **20:20 平局**（管道用毫米、风管用米）→ **平局就不硬选全局答案，退回逐元素对照外接盒判断**。

**诚实标注**：这是个"不可能完美自动判断"的脏数据问题，系统选择在没把握时不猜全局值，避免整批算错；结果经 `scale_info` 透出，供人工复核。

## 四、第二环 · 测：怎么证明"读全了"

### 4.1 实体覆盖度（QA 报告新增）

模型体检报告里加了一页 `entity_coverage`，自动列出"文件里有、但我们认出的"（handled）和"文件里有、我们没认出的"（unhandled）：

```
Lab.ifc → handled: {墙12, 管段173, 管件135, 风管108, 柱3, 门3, 板2, 窗1}
          unhandled: {}   ← 空的 = 每一类都认出来了
```

**局限（重要）**：这只证明"实体类型都认识"，**不代表每根管身上的属性都读到了**。为此做了**属性层彻查**：不预设字段名，把文件里所有属性集名全列出、逐根翻属性，确认 Lab 管道身上只有 `OuterDiameter`（直径）和 `Created By`（谁建的）两个属性——**系统信息文件导出时就没写**，不是我们读漏。判断"数据缺失 vs 读取遗漏"的正确方法是**无预设地全量翻检**。

### 4.2 测评脚本：6 维度打分

新增 `scripts/benchmark_ifc.py`，对每个 IFC 跑完整管线，按 6 科加权打分（满分 100），并给一个成绩等级 S / A / B / C / D（90 分以上为 S，就像考试评级），方便不同模型横向比较：

| 科目 | 权重 | 考什么 |
|---|---|---|
| A 健壮性 | 20% | 能打开、解析、审查不崩 |
| B 提取完整率 | 25% | 每类实体读到多少（最高权重，呼应"读全没有"）|
| C 字段填充率 | 20% | 读到的元素身上字段满不满 |
| D 准确性 | 15% | 数值像不像真的（合理性代理）|
| E 规则激活率 | 15% | 规则有没有真的在判 |
| F 性能 | 5% | 解析快慢（秒/MB）|

**Lab.ifc 各科得分**：A=100（不崩）｜ B=100（实体全读全）｜ C=63（字段欠齐）｜ D=98（尺寸基本合理）｜ E 见下｜ F=90（4.2s 解析 1.1MB）

### 4.3 一次公平性修正（E：21 → 43）

初次跑出 **E 只有 21 分**——规则库近半数是要"查房间"的（疏散/无障碍），而 Lab 是纯机电模型**没有房间**，"无米下锅"。若把房间类规则算进分母，等于因文件没画房间而扣分，不公平。

**修正**：E 只对"模型确实有那类数据、规则才可能触发"的规则算分母。Lab 无房间 → 房间类规则不进分母。**21 → 43**。

## 五、第三环 · 查：发现一个规则死角

E 修到 43 后，逐个打开 MEP 规则看"谁真的判定过管道、谁没有"，发现一张反常的表（judged = 这条规则实际判定了几根管）：

```
MEP-001 消防管最小管径    judged= 0   ← 一根都没判
MEP-002 排水管最小坡度    judged= 0   ← 一根都没判
... （管径/坡度类几乎全 0）
MEP-008 系统类型明确      judged=173  ← 判了!173 根全判
```

**表面的假象**：MEP-008 判了 173 根，看起来 MEP"有在干活"。

**实际的问题（本质）**：
- MEP-008 只是"查你有没有系统标签"，173 根全 unknown = 它喊了 173 声"你们都没名牌"，但**没有检查任何一根管的真实质量**。
- 真正查质量的规则（管径够不够、坡度对不对）触发条件全部是"必须先知道系统类型"（`pipe_type==fire/drainage/supply`）→ 管子没标签 → 全跳过。
- **结果：173 根管道没有一根被真正检查过尺寸和坡度——它们是"无主孤儿"。**

**一句话**：规则把"查质量"和"知道系统类型"绑死在一起，导致没标签的管就没人查。

## 六、第四环 · 修：补"先做人，再问名"的兜底规则

针对上面的死角，补 3 条**不看系统标签、对所有管道一视同仁**的普适兜底规则（cn/sg 各 3 条，MEP 规则 10 → 13）：

| 规则 | 查什么 | 判定 | 设计理由 |
|---|---|---|---|
| **MEP-011** 通用水管最小管径 | 管径 < **10mm** → 违规(High) | 废数据红线 | 比 10mm 细的几乎不可能是真水管（0.2mm 建模假管）；若定 15mm 会误伤 12.7mm（1/2 英寸）合规细管 |
| **MEP-012** 通用水管明显反坡 | 坡度 < -0.005 → 违规(High) | 反坡必错 | 加压管允许 0 坡，但反着流物理上必错 |
| **MEP-013** 通用水管水平提示 | 坡度接近水平 → 提示(Low) | 人工确认 | 水平可能是合法加压管（消防/给水），也可能是缺坡的重力排水管——不直接判违规，请人确认 |

**分层逻辑（"先做人、再问名、后行礼"）**：
```
第一层 MEP-011/012/013  先做人：不看标签，先体检（粗细、流向）
第二层 MEP-008          再问名：你没系统标签 → 点名
第三层 MEP-001~009      后行礼：知道是消防/给水 → 专项合规
```

**实测效果**：173 根 unknown 管终于被真正检查——**11 根废管径 + 29 根反坡被揪出**；平台总分 **83.3 → 88.6**。

## 八、诚实标注：这份 Lab.ifc 测不出什么

这份文件是**纯机电、无系统标签、无房间**的极端情况，如实说明边界：

| 项 | 为什么做不了 |
|---|---|
| 房间级规则（疏散/无障碍）| 文件无 IfcSpace（0 房间），无米下锅 |
| MEP 专项规则（消防管间距等）| 需识别系统类型，文件没给任何系统信息/名称/分组 |
| 设备规则 | 文件无泵/风机/水箱等设备实体 |
| 系统归类 | 管道全 PVC、无系统对象，无法从数据区分消防/给水 |

**这不是平台缺陷，而是文件本身的信息边界**——几何与材料完整读出，但"这根管是消防还是给水"这类语义，模型从未记录。

## 九、给老师的话

这轮工作最大的价值不是"多读了几类实体"，而是把一个 **"看着查了、实则没查"的规则死角**补上了：

> 过去，只有"知道系统类型"的管道才会被审查；没贴标签的真实管道成了规则真空。现在补了"先做人再问名"的兜底层，任何管道先接受基础体检（粗细、流向），再谈专项合规。

**一句话总结**：真实 MEP 模型让平台从"自证会读"走到"**能测、能审、能诚实标注边界**"——对一个没有房间、没有系统标签、单位混乱的真实文件，做到了实体 100% 读全、单位判断诚实、规则闭环补全。

**下一步的两个可选方向**（供讨论）：
1. **把这类真实模型纳入常备测试集**——Lab.ifc 这种"不完美但真实"的文件比自造样例更能暴露平台短板，建议固定留存，每次改提取器都跑一遍测评防止回归。
2. **找一份带系统标签的 MEP 模型**——Lab.ifc 管道无系统信息，专项规则（消防管间距、排水坡度）没法真实验证。若后续能拿到带 System Name 导出的模型，就能把第三层"专项合规"也实测一遍。
