## 一、总体目标与优先级

本阶段两条工作线并行，主次分明：

1. **Viewer 线（导师最关注的可视校验）**：**先把二维做扎实**——鼠标悬停（cursor hover）就要有反馈、有具体内容；二维收尾后转向三维，**三维是本阶段真正的重点和亮点**，并探索在三维层面引入 AI。
2. **AI 语义线（上周工作的收尾）**：语义层融入 AI 的工作**必须全部做完**——大样本验证、词表补全、归一化位置前移。

排序原则：**二维 hover 快速收尾（短期）→ 三维开源调研立即启动、先行铺路（本周就开始）→ 三维原型 + 三维 AI 作为中期核心产出。** 语义层收尾与三维调研并行，互不阻塞。

## 二、工作线 A：Viewer —— 二维先做好，再上三维

### A1. 二维交互收尾（短期，优先做完）

现状：网页结果页已有"交互查看"Tab（Pillow 高清平面底图 + plotly 透明热区），但悬停反馈和内容还不完整。

要做到：

- 鼠标移到任意构件上：**光标变为可点选状态 + 立即浮出 tooltip**，无需点击即可看到基础信息；
- tooltip 至少包含：构件名称、IFC 类型、所属楼层、关键几何尺寸（如墙厚×长、柱截面、门宽）、互检状态（✓/✗/漏/多，错的给出"真值→提取值"）；
- 点击构件：右侧/弹出**详情面板**展示完整内容——三轴尺寸、GlobalId、材料（含 AI 归一化后的 material_class 及"AI 识别"小标注）、触发的审查规则 ID 与标题、规范条文；
- 兼容无房间/边缘模型（此前 Lab.ifc 等显示异常需修掉）；
- （上周遗留）双向联动：点左侧问题列表中的某条违规，平面图上**高亮定位**对应构件。

验收：用 FZK 演示，悬停墙/门/柱即有 tooltip，点击能看到尺寸与触发规则；问题列表点条目图上有高亮。

### A2. 三维可视化（本阶段核心，先调研后动手）

目标：从"楼层平面图"升级到"建筑三维模型里直接看构件、看审查结果、看 AI 结论"。

**第一步（立即启动）：开源仓库调研，形成选型报告。** 候选方向（待调研，不预设结论）：

| 候选 | 技术形态 | 重点考察 |
|---|---|---|
| **That Open Engine**（原 IFC.js / web-ifc） | Web 端纯 JS 解析渲染 IFC | IFC 支持完整度、可否与 Streamlit/前端集成、社区活跃度、license |
| **xeokit-sdk** | Web 大模型 BIM 查看器（BIMData 等在用） | 大模型性能、构件拾取/高亮/剖切、元数据访问、商用 license |
| **Speckle** | BIM 数据互操作 + 3D viewer | 生态/连接器、是否过重、Python 侧可用性 |
| **three.js（裸）** | 通用 WebGL | 自研成本：IFC 解析、拾取、标注都要自己做，作为对比基线 |
| **FreeCAD / Bonsai（原 BlenderBIM）** | 桌面端开源 BIM | 桌面级能力强，但与 Web 汇报形态的差距 |

调研必须回答的问题：

1. IFC 几何能否完整加载（含 Archicad/Revit 老导出、斜构件、MappedItem——正是我们互检修过的难点）；
2. 能否**按 GlobalId 拾取单个构件**、高亮、变色、悬浮标签（二维互检标注要在三维复刻）；
3. 与现有 Python/Streamlit 架构怎么接（内嵌 Web 组件 vs 独立前端）；
4. license 是否允许学术/后续商用；
5. 性能：FZK（百件）→ Revit-MEP（2000+ 管件）量级是否流畅；
6. 有没有可挂 AI 的接口位（见 A3）。

调研产出：`docs/规划与技术/` 下一份三维开源选型报告（候选对比表 + 在我们 2–3 个真实 IFC 上的最小加载实测 + 推荐方案与理由）。

第二步（调研通过后）：三维查看器最小原型——加载 IFC、按构件着色（互检对错/违规状态）、点击看详情。

### A3. 在三维层面引入 AI（中期亮点，随三维原型探索）

可能的方向（调研后收敛，不承诺全做）：

- **三维场景内的自然语言交互**："找出所有宽度不足的疏散门"→ AI 解析意图，三维中定位高亮对应构件；
- **AI 审查结论三维挂载**：点击构件，AI 用通俗语言解释"它违反了哪条规范、为什么"（判定仍由确定性规则给出，AI 只解释，守住"模型负责读懂、规则负责判"的边界）；
- 三维中框选区域/房间 → AI 汇总该区域的问题清单。

红线与二维/语义层一致：AI 不判定、不改几何数字、结论可追溯到规则与条文。

## 三、工作线 B：AI 语义预处理层收尾（上周遗留，"要做完"）

现状：`agents/enricher.py` 已落地房型 + 构件材料两类归一化，接 DeepSeek 官方 API，34 题金标验证通过；管道归一化架构已通；旧的可见仲裁 UI 已撤除。

| # | 任务 | 内容 | 验收 |
|---|---|---|---|
| B1 | **31 个真实模型大样本实测** | 在线批量跑全集，统计每个模型的候选数 / AI 救回数 / 诚实弃权数 / 越界拒绝数 / 缓存命中 | 出一份大样本统计表；验证小样本结论（精确率高、乱猜≈0）在大样本成立；发现的乱猜案例回收进金标 |
| B2 | **房型受控词表扩住宅类** | 增补 Living Room / Bedroom / Kitchen / Dining / Storage / Reception 等，配套多语言关键词（德/中）、扩充金标考题；**同步新增或放宽对应审查规则**——不能只扩词表不接规则 | 住宅模型（Jasmin、Duplex 等）的 living room/bedroom 能正确归类且有规则消费；金标重跑乱猜仍为 0 |
| B3 | **归一化位置前移评估** | 评估把同一套归一化从 `build_review_data` 之后前移进 `parse_model`，使互检"分类"维度（当前约 24.2%）与审查引擎同时受益 | 给出前移/不前移的结论与成本；若前移，互检分类指标有量化提升且无回归 |
| B4 | 管道系统归一化实测 | 第 3 类语义在真实 MEP 模型上在线验证（fire/water/drainage/hvac/electrical） | MEP 模型 unknown 管道比例下降，归类经抽检正确 |
| B5 | 客户自由描述入口 | 第 4 类语义（通用"描述→类别"批量入口）本期仅预留，不做 UI | 接口在、默认不启用 |

完成标准（Definition of Done）：语义层四类中前三类（房型/材料/管道）在真实模型上全部跑通并有量化报告；几何数字零改动、真实模型违规总数零回归这两条安全承诺在大样本上复核通过。
