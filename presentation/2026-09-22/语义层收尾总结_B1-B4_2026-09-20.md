## 三、B3 · 归一化位置前移评估 —— 结论：不前移

### 现状
```
parse_ifc → parse_model → build_review_data → enrich_review_data → run_full_review
                              (bdata)            ↑ 归一化在这里
互检 crosscheck 读的是 parse_model 的 struct --- 看不到归一化 ---
```

### 为什么「前移能让互检分类维度受益」这个假设不成立
互检的分类维度**两侧算法不同源**：
- **真值侧**：`_classify_room_type(name + ifc_type)` —— 关键词
- **提取侧**：`_classify_room_type(ref + name + long_name)` —— 关键词

若把归一化前移，提取侧变成 AI 值、真值侧仍是关键词 → **AI 救回的条目反而会变成新的不匹配**，指标下降而非上升。

### 真正的瓶颈：真值侧保真度（已修）
实测 Jasmin：真值侧只读 `elem.Name`（`'101'`），**没读 `LongName`（`'Wohnen/Essen/Kochen'`）**，
而提取侧读了 → 真值全 Unknown、提取是 Living Room → 一致率仅 **50%**。

**修复**（`scripts/crosscheck_ifc.py`）：
- `read_ifc_truth` 存下 `long_name`
- `room_type_truth` 改用 `long_name + name + ifc_type`（与提取器同证据源；LongName 缺失时退化为旧行为，不会更差）

**效果**：Jasmin 分类一致率 **50% → 100%**。

### 前移的成本（供决策）
| 成本 | 说明 |
|---|---|
| 架构耦合 | 提取器（纯确定性、离线）会依赖 LLM 客户端 |
| 延迟 | LLM 调用（数秒/栋）进入解析主路径 |
| 收益存疑 | 唯一论据（互检分类受益）已被证伪；审查引擎本来就在富化之后跑，不受影响 |

**结论**：本期**不前移**。互检分类的真实问题用「真值侧补 LongName」这个更便宜的方式解决，已落地。

## 四、B1 · 31 模型大样本实测

### 关键 bug 修复：LLM 响应截断 → 分块调用
大样本实测暴露出一个**致命问题**：候选多的模型（HITOS 549、Smiley 90、Institute 76 个候选）
**全部 `ai_resolved=0`**。定位到根因：

> `LLM_MAX_TOKENS=1600` 下，一次请求上百个候选会让响应 JSON 被**截断**（实测 80 个房间在 k53 处断），
> `_parse_json` 解析失败 → 整栋楼放弃。

**修复**（`agents/enricher.py`）：把候选切成 40 个/块，逐块调用 + 按内容哈希分块缓存。
- 修复前：80 候选 → 0 处理
- 修复后：80 候选 → 60 正确归类、20 裸「Zimmer N」正确弃权

### 大样本统计表（2026-09-20 全量跑完）
数据：`output/enrichment/batch_full.json` / `batch_full.log`

| 指标 | 数值 |
|---|---:|
| 模型数 | 31（**29 解析成功**；2 个 IFC2X_FINAL 架构不支持） |
| 候选总数 | 933（房型 277 / 材料 528 / 管道 128） |
| **AI 救回** | **200** |
| **诚实弃权** | **733** |
| **越界拒绝** | **0** |
| 缓存命中 | 98 |
| 用上 LLM 的模型 | 10/31（其余 21 个无房型/材料/管道候选，无需调用） |

**对比修复前**：`AI 救回 3 → 200`、`越界拒绝 600 → 0`。修复即上文的分块 + token 预算。

典型模型：
| 模型 | 候选 | 救回 | 弃权 | 拒绝 |
|---|---:|---:|---:|---:|
| HITOS-Large-Building | 549 | 88 | 461 | 0 |

### 小样本结论在大样本成立
- **精确率高**：金标 100%；大样本救回集中在有明确文本证据的条目
- **乱猜 ≈ 0**：金标乱猜 0；大样本「越界拒绝 0」意味着 AI 没有输出证据之外的枚举值
- **诚实弃权是主流**：733/933 弃权——多数真实模型的房型是纯数字编号、材料是通用名，AI 按策略弃权而非猜测

### 另一处统计 bug 修复
`_merge` 的管道循环**没做候选校验**，把非候选管道（已有关键词分类的）全记成「越界拒绝」——
Duplex_MEP 425 管道里 18 个候选，却被记 **407 次拒绝**。已加 `pipe_keys` 校验。

## 五、B4 · 管道系统归一化实测

### 关键 bug 修复：PIPE_VOCAB 与规则词表不一致
enricher 的 `PIPE_VOCAB` 原为 `["fire","water","drainage","hvac","electrical","unknown"]`，
但：
- 确定性分类器（`bim/extractor.py:_PIPE_TYPE_RULES`）产出的是 `fire/drainage/supply/hydronic/gas/lab_gas/vent`
- MEP 规则消费的也是后者（`MEP-006` 用 `supply`、`MEP-009` 用 `fire`）

**后果**：AI 填的 `water/hvac/electrical` 会被枚举校验丢弃，**整条管道语义层是死的**。
已把 `PIPE_VOCAB` 对齐为 `["fire","drainage","supply","hydronic","gas","lab_gas","vent","unknown"]`。

### 实测：unknown 管道比例下降
| 模型 | 管道总数 | unknown（前→后） | 说明 |
|---|---:|---|---|
| **Revit-MEP-Sample_IFC4** | 868 | **126 → 77（15% → 9%）** | AI 把「Pipe + 铜管材料」归类为 supply/hydronic |
| Duplex_MEP | 425 | 18 → 18（4%） | 18 个全是**电气线管（Conduit）**，超出管道词表 → **诚实弃权** |
| Building-Hvac_IFC2x3 | 1 | 1 → 1 | 单管道，无系统线索 → 弃权 |

**抽检正确性**：Revit 新归类的 49 条均为 `Pipe + ML-Copper pipes …`（铜管）→ `supply`——
铜管在建筑 MEP 中即给水管，属**基于材料的合理推断**（提示词允许材料作为证据），非乱猜。

**验收达成**：MEP 模型 unknown 管道比例下降（Revit 15%→9%），归类经抽检正确，弃权条目（电气线管）确无管道系统线索。
